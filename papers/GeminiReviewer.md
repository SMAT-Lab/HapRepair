# 审稿意见：HapRepair

## [Summary]
本文针对“低资源”编程语言（以 OpenHarmony 的 ArkTS 为例）中缺乏大规模修复语料、可执行测试套件及成熟分析工具链的挑战，提出了一种基于“静态预言机（Static Oracle）”引导的 LLM 自动修复范式。核心思想是将“修复位置（Where-to-fix）”与“修复方式（How-to-fix）”解耦：利用高精度的静态分析工具（HomeCheck）作为确定性的契约来定位缺陷并提供校验反馈，同时利用 LLM 结合 RAG（检索增强生成）来合成具体的修复代码。通过构建包含 426 个手动编写的缺陷-修复对的知识库，缓解了训练数据稀缺的问题。在 35 个真实的 OpenHarmony 项目上的评估表明，HapRepair 在经过 5 轮迭代后消除了约 97% 的静态违规，且在人工抽样检查中保持了较高的语义正确性。

## [Strengths]
1.  **极具现实意义的问题定位与场景切入**：文章敏锐地指出了当前 APR（自动程序修复）研究多集中于 Java/Python 等成熟生态的局限性，并将目光投向了测试基础设施薄弱、数据稀缺的新兴语言生态（Low-Resource Languages）。在缺乏可运行测试（Test-Scarce）的场景下探索自动化修复，是一个具有高度实用价值且富有挑战性的 SE 问题。
2.  **方法论设计清晰且务实**：提出的“Static-Oracle-Guided”范式在方法论上是合理的。文章明确了在测试缺失时，将“静态分析通过”作为修复的“可检查契约（Checkable Contract）”是一种必要的妥协，并通过“精度优先（Precision-first）”的预言机设计原则来降低误报带来的破坏性风险，这种设计权衡体现了深思熟虑的工程哲学。
3.  **系统的评估与消融实验**：作者在真实的工业级项目（OpenHarmony）上进行了大规模评估（8,664 个缺陷），不仅比较了不同 LLM 的表现，还对 RAG 的检索策略、上下文提取方式、Diff 引导等组件进行了细致的消融分析，为后续研究提供了有价值的实证经验。
4.  **不仅是工具，更是设计原则的提炼**：文章并未止步于实现一个工具，而是在 Section 2.4.1 中提炼了静态预言机支持 LLM 修复的四个可复用属性（Precision over recall, Stable identifiers 等），提升了论文的理论深度和对其他语言生态的参考价值。

## [Weaknesses]
1.  **“合规性（Compliance）”与“正确性（Correctness）”之间的鸿沟**：虽然作者诚实地指出了静态预言机只能保证规则合规而非行为正确，但在 APR 领域，仅仅消除静态警告（Silence Warnings）并不等同于修复了 Bug，甚至可能引入语义退化（如简单删除代码）。尽管 Section 5.3.1 进行了人工抽样验证，但对于缺乏测试保障的大规模自动化修复，如何从根本上规避“为了修复而破坏逻辑”的风险，文中讨论仍显不足。
2.  **知识库构建的成本与“低资源”定义的张力**：文章通过 RAG 缓解数据稀缺问题，但依赖于手动构建的 426 个高质量缺陷-修复对。虽然这比训练大模型便宜，但对于每一个新的低资源语言或新的规则集，都需要专家介入构建这样的知识库。这种“手动冷启动”的成本是否真正解决了低资源问题，或者只是转移了成本？这一点值得商榷。
3.  **对静态分析工具（HomeCheck）的高度依赖**：整个流程的有效性完全建立在 `HomeCheck` 能够达到 100% 精度的假设上。如果静态分析工具本身存在漏报或误报，流程的鲁棒性将大打折扣。这意味着该方法的推广门槛在于必须先为该语言构建一个极高质量的静态分析器，这本身就是一个巨大的工程挑战。
4.  **基线对比的局限性**：目前的对比主要是自身变体（Ablation）和不同 LLM 之间的对比。虽然缺乏同类工具是客观事实，但未讨论与传统的非 LLM 静态修复工具（如基于模板的自动重构工具）的理论或定性对比，使得读者难以评估 LLM 在此场景下的不可替代性到底有多大（例如，多少比例的修复是模板无法覆盖而必须由 LLM 完成的？）。

## [Major Concerns]
1.  **语义正确性的验证逻辑**：
    在 RQ2 的回答中，作者强调了“guideline-compliance repair rate”作为主要指标。然而，对于 TOSEM 读者而言，最关心的是修复是否改变了程序的预期行为。Section 5.3.1 提到只有 2.2% 的回归率（Regression rate），这个数据主要基于人工阅读代码。但在没有动态测试的情况下，人工很难发现隐蔽的运行时错误（如逻辑死代码、资源泄露的错误处理）。建议增加更深入的讨论：在完全无测试环境中，这种方法的安全边界在哪里？是否存在某类规则是绝对不应使用此方法修复的？

2.  **RAG 数据集与评估集的数据泄漏风险**：
    虽然作者声明测试集是 "strict hold-out"，但 RAG 检索库包含了 426 个手动构建的对。需要明确说明这些手动构建的对是否源自与测试项目相似的编码模式或库版本。在低资源语境下，代码模式的重复度可能很高，如果 RAG 检索到的示例与待修复代码过于相似（Near-duplicate），那么 LLM 的泛化能力评估可能会偏高。

## [Minor Comments]
1.  **模型版本说明**：文中使用了 "GPT-5.1" 和 "GPT-5-mini"。假设这是基于当前时间点（2025年）的真实模型，请确保在最终版本中对模型具体参数或访问方式有清晰引用，以便未来复现。
2.  **图表清晰度**：Figure 4 展示了不同 LLM 的迭代收敛情况，但线条较为密集，建议增加更清晰的标注或拆分展示。
3.  **术语一致性**：文中混合使用了 "Static Oracle" 和 "Linter"，建议统一术语体系，明确 HomeCheck 在本框架中特指作为 Oracle 的角色。
4.  **案例分析**：Section 5.5 的讨论非常有价值，特别是关于“何时需要 LLM vs 模板”的分类。建议增加具体的代码示例来直观展示“LLM-needed”类别中，模板方法为何会失败。

## [Recommendation]
**Minor Revision**

**理由**：
这是一篇扎实的工作，解决了 SE 领域中一个重要且被忽视的角落（低资源语言的修复）。其提出的“静态预言机引导”范式逻辑自洽，实验充分。
虽然存在关于“语义正确性”的理论担忧，但在设定的“无测试”约束下，作者的方法已经是当前最优的可行解之一。我建议进行**小修（Minor Revision）**，主要要求作者更深刻地讨论方法的局限性（特别是静态合规与动态正确性之间的差距），并澄清 RAG 数据的构建细节以及与传统模板方法的界限，以进一步提升论文的理论严谨性。
