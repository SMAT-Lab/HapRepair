	本文档为国家重点研发计划重点专项“面向国产软件生态的基础软件质量保障技术”项目中“任务4: 基于修复样例检索的国产基础软件故障修复技术”的相关技术文档，该任务由北京航空航天大学大学牵头并完成。本文档作为故障修复样例数据集及相关文档说明，涵盖数据来源、收集方法、组织结构、存储格式、质量控制及使用规范等方面，以确保数据集的可理解性与实用性。
一、背景介绍
简要介绍任务中的研究内容，引出为何需要构建该数据集以及数据集大概的构建和收集方式。
	对于以程序作为测试用例的编译器来说，故障触发与程序中特定结构等特征相关，因此，构造包含揭错特征的测试程序将显著提升这类基础软件的测试效果。然而，国产基础软件往往处于初期，尚未有足够历史故障支持挖掘揭错测试特征。基于不同语言编译器的功能及测试特征的相似性，本研究利用其他语言编译器的海量历史故障挖掘揭错特征。由于不同语言间的差异，其他语言编译器的揭错测试程序无法直接用于测试国产编译器，因此本研究提出“抽象—实例化”的工作流实现跨编译器揭错特征的迁移。具体来说，本研究通过程序分析识别出其它语言编译器的揭错测试程序中的控制结构、数据依赖等特征，并利用LLM 的代码摘要能力，将揭错特征转化为自然语言描述，从而屏蔽不同语言间的差异。进而，本研究利用LLM 的代码生成能力，使用自然语言描述的揭错特征引导LLM 生成包含这些特征且符合国产编译器对应语言规范的测试程序。
	为支持跨语言揭错特征迁移研究的开展，本任务首先对现有主流编程语言编译器的故障进行挖掘分析，进而整理成待迁移的编译器故障数据集。具体来说，本研究选取两种主流的编程语言：C/C++与Java作为收集对象，挖掘这两类编程语言编译器的缺陷数据。选择这两种语言的主要原因在于，一方面，C/C++与Java经过多年的演化、发展，已经拥有成熟活跃的编译器生态和开源社区（如 GCC、LLVM/Clang、OpenJDK、Eclipse JDT 等），积累了大量真实的历史故障样本与测试用例，便于系统化的数据收集与分析；另一方面，两种编程语言涵盖了主流编程语言的大部分语言特性，为跨语言揭错特征的抽象与迁移提供了丰富的维度与研究价值。在完成编译器故障数据集的构建后，本研究将进一步利用大语言模型（LLM）强大的代码理解与语义抽象能力，对数据集中不同类型的故障样本进行自动化分析与特征归纳，从中提炼出具有代表性的揭错特征模式。基于这些特征，开展跨语言迁移实验，指导生成符合国产编译器语言规范且包含潜在揭错特征的测试程序，从而提升国产编译器的测试覆盖度与揭错能力。
为此，本研究通过对C/C++与Java的代码仓库缺陷（如 GCC 与 LLVM/Clang 的 Bugzilla 与 GitHub Issues，以及 OpenJDK、Eclipse JDT 等 Java 编译器的 JIRA 平台）进行系统化挖掘，重点收集与编译器前端解析、中间表示优化、后端代码生成等阶段相关的崩溃、误编译与错误优化等故障信息，识别带有揭错测试用例的缺陷记录。针对收集到的大量故障样本，本研究进一步开展数据清理与结构化整理，对重复、无效及无法复现的样本进行筛除，并依据故障类型、语言特征等信息进行归类。通过利用大模型强大的程序分析能力，对测试程序的语法、语义特征进行分析，从而提炼出揭错测试程序的揭错特征模式，为后续的特征迁移与测试生成提供高质量的基础数据支撑。

数据来源：说明数据来自何处（如开源项目、编译器测试套、人工生成程序等）；收集流程：描述数据的收集方式（爬取、测试生成、差分测试、模糊测试等）；收集工具：列出所使用的工具或平台（如 Csmith、YarpGen、自研工具等）；数据收集时间范围：注明数据的收集时间周期。
本节详细阐述了编译器故障数据集的数据来源、系统化的收集流程、所使用的工具平台以及具体的收集时间范围。
2.1 缺陷数据来源
本研究中的缺陷数据主要来源于三个主流开源编译器/虚拟机项目的官方缺陷跟踪系统，具体如下：
●GCC (GNU Compiler Collection): 通过其官方Bugzilla缺陷跟踪系统（）获取历史缺陷报告。
●Clang/LLVM:通过其GitHub Issues平台（）获取缺陷记录。
●HotSpot JVM (OpenJDK): 通过其JIRA缺陷追踪系统（）获取相关缺陷信息。
此处选择该三个项目的原因为其拥有大量丰富的历史缺陷报告（数十万量级）。而其他项目相比这三个项目而言，历史缺陷报告数量相对较少，代表性弱，故不选择。
2.2 收集流程与方法
揭错特征数据集的收集过程主要分为两个关键阶段：候选缺陷报告筛选和揭错特征提取。接下来简单介绍这两个阶段的具体任务。
1.候选缺陷报告筛选：由于各平台的历史缺陷报告数量过于庞大，且包含大量非功能性错误（如文档、性能优化、咨询等），本研究采用自动化预筛选流程，以确定高优先级的、与编译器故障直接相关的候选缺陷集，作为后续特征提取的基础。
2.揭错特征提取：针对第一阶段筛选出的所有候选缺陷，基于大语言模型（LLM）执行自动化的揭错特征提取流程。该阶段的输入为缺陷报告摘要（标题、描述、前5条关键评论），输出为LLM总结得到的揭错特征自然语言描述以及其相关的原始代码片段。
2.2.1 候选缺陷报告筛选
由于三个项目的历史缺陷跟踪系统结构各异，拥有不同的特点，因此下面分别介绍不同项目的筛选处理。
对于HotSpot项目而言，其历史缺陷追踪系统中存在大量与故障无直接相关的报告（例如JEP提案、JLS设计、构建错误等），其中部分报告无法直接通过跟踪系统的标签筛选。且揭错特征的提取依赖于包含测试程序的缺陷报告，如果缺陷报告中未附有可复现的测试程序，则该报告对于特征提取没有贡献。然而并非所有缺陷报告都符合规范要求，导致测试程序存在的形式各异（部分以文本形式附在报告正文中，部分以附件形式存在）。因此直接对跟踪系统设计筛选流程存在成本较高。
通过调研发现，目前已经有相关工作（JOpFuzzer）对HotSpot项目的缺陷报告进行了系统性的整理和统计。该工作将HotSpot项目中存在测试程序的缺陷报告进行了整理，最终得到了包含测试程序的866份缺陷报告。该工作将每份缺陷报告所包含的全部测试程序存储于按缺陷报告命名的文件夹中。因此，本研究通过反向爬取的方式，基于先前研究已筛选的结果，将这些缺陷报告直接作为候选缺陷报告集。并基于构建的缺陷报告集作为下一阶段揭错特征提取的来源。
对于GCC与Clang项目，二者由于缺陷报告的目标语言均为C++，因此其筛选流程存在相似部分。但由于GCC使用较早的Bugzilla作为跟踪系统，而Clang使用Github Issue，二者在原始的缺陷报告收集上存在些许差异。针对GCC，本研究使用其Bugzilla自带的CSV导出功能，初步得到属于C++组件、并且已修复的缺陷报告列表。该CSV文件包含了缺陷的编号、标题以及最后更改时间等信息。而针对Clang的缺陷报告，由于Clang项目的Issue与LLVM中其他子项目共用相同仓库，因此本研究设计了一套筛选出已修复、属于Clang C++组件的缺陷报告的方法。具体来说，本研究利用Github的高级搜索语法，结合Issue状态、标签等信息，初步获取高质量的缺陷报告信息。最终将获取到的缺陷报告信息参考GCC导出的CSV格式进行存储，便于后续流程的统一处理。
上述步骤得到的缺陷报告数量相对来说仍然非常庞大，例如GCC共导出了13660份缺陷报告；Clang共导出了3941份缺陷报告。由于上一步骤只使用了简单的筛选方法，其中可能包含无测试程序或非编译器故障的误报缺陷，因此本研究进一步对这些报告进行了筛选。本研究采取逐层深入的方法，降低成本，先基于标题、标签等已爬取的轻量信息进行评分并筛选低分样本，最终使用评分进行排序，得到最终用于提取揭错特征的缺陷报告。接下来介绍该细粒度的筛选方法。
具体来说，本研究设计了一套评分机制，针对不同的缺陷报告进行评分，并过滤掉低分报告。设计的评分机制具体如下，将崩溃（Crash）作为最优先的缺陷类型，其次为错误编译（Miscompilation），通过检索标题中的关键词（Crash、ICE、SegFault、Miscompile等）来给予奖励分数，对于Clang的缺陷报告而言，还额外使用了其标签（crash-on-invalid、crash-on-valid等）作为指标。最终每份缺陷报告都会被赋予一个可量化的分数，通过人工设置评分阈值，过滤掉评分位于该阈值下的缺陷报告，并且对其按照分数降序排序，最终GCC和Clang分别得到了5513份和1742份缺陷报告。尽管已经经过了多层的过滤，但GCC和Clang由于其庞大的历史缺陷报告库，过滤后的数量仍然过多，因此参考HotSpot项目所获取的缺陷报告量级，本研究最终选择了GCC和Clang中评分排名前500的缺陷报告作为下一阶段揭错特征提取的输入。
2.2.2 揭错特征提取
本阶段的主要任务为基于上一阶段筛选出的高质量候选缺陷报告（总计1866份），执行自动化的揭错特征提取流程。经过了上一阶段的预处理，这些缺陷报告的格式大致相同，因此后续的提取流程相对一致。接下来具体介绍揭错特征提取的方法和实现。
首先，本研究对缺陷报告进行了完整爬取。上一阶段中的缺陷报告，只包含了缺陷编号、缺陷标题、修改时间等元数据，并未爬取其具体的描述、评论、附件等内容，因此本研究针对不同平台设计了爬取指定编号缺陷报告的接口，用于后续LLM的缺陷特征提取任务。下表给出了不同项目用于爬取缺陷报告的API接口，以及其返回格式。通过这个接口，本研究可以获取指定编号缺陷报告的全部内容，包括了标题、描述、评论以及附件（如果存在）。
项目	API接口	返回格式
GCC		XML
Clang		JSON
HotSpot		JSON
接下来本研究对缺陷报告进行了关键内容摘要。这里进行摘要的原因为原始缺陷报告中存在大量重复、无用的内容或噪声。例如GCC缺陷报告中的评论，如果包含了对之前某一条评论的回复，则会对该回复进行一次复制，形成重复；Clang缺陷报告的评论中包含了其仓库机器人的自动回复或订阅信息，该部分信息为对原始报告的标题和描述的复述。其次针对编译器崩溃的缺陷报告，通常附有冗长的Stack Dump信息，这部分信息对于开发人员调试或许有帮助，但对于输入上下文有限的LLM而已，容易使其关注点偏离与揭错直接相关的测试程序。因此本研究将上述提到的这些信息进行了简略或过滤，减少输入给LLM的噪声。具体来说，最后的缺陷报告摘要只包含了以下几个部分：（1）标题（2）报告描述（3）前5条过滤后的评论（4）附件中的测试程序（如果存在）。
最终本研究基于缺陷报告摘要使用大语言模型（qwen-plus模型）进行揭错特征提取。本研究结合当前流行的提示技术，例如思维链（Chain-of-Thought, CoT）和少样本（Few-Shot）构造了揭错特征提取提示（Prompt）。该提示要求LLM使用思维链的方式对缺陷报告进行分析，首先判断错误根因，接下来根据上下文信息定位缺陷位置，并提取与缺陷直接相关的代码片段，最终通过使用自然语言的形式高度概括和总结该代码片段，最终得到揭错特征。同时该提示中包含一份缺陷报告提取揭错特征的示例，引导大模型更好地进行特征提取。在这一过程中，大模型的最终输出有两部分内容：(1) 导致缺陷的最小化揭错代码片段（即测试程序的核心部分）；(2) 对该引发缺陷的代码片段总结概括的自然语言描述（即“揭错特征”）。为保障数据质量，若无法从缺陷报告中获取有效信息（如不包含有效测试程序或误报情况），LLM将输出预设的特殊标记字符串，以便于后续自动化脚本识别并筛除无效特征。最终本阶段从GCC、Clang、HotSpot项目当中分别成功提取479、480、658条揭错特征。

五、质量控制与验证
数据清洗：描述对无效样本或重复样本的处理；验证方法：介绍验证故障样本真实性与可复现性的机制；人工检查：说明是否进行了人工标注或审查。
本研究中的采用了多种方式对缺陷报告及揭错特征进行质量控制。下面具体介绍所有阶段中采取的质量控制方法。
对于预筛选阶段，该阶段过滤掉了与故障无关的缺陷报告，同时优先选择高优先度的缺陷报告作为后续的特征提取来源。对于重复样本的处理，主要依赖于错误跟踪系统中开发人员对于缺陷报告的标注，如果某个缺陷与之前的缺陷具有相同的根因，开发人员则会将其状态设置为重复（Duplicated），通过过滤该类状态的缺陷报告可以去除重复的缺陷报告。
对于揭错特征提取阶段，本研究借助LLM强大的上下文理解能力，让LLM使用思维链的方式，通过分析缺陷报告是否包含用于复现的测试程序代码、是否提供完整的复现步骤以及是否含有具体的错误描述等方式，判断该缺陷报告是否满足提取揭错特征的条件。该方法将细粒度过滤缺陷报告与提取特征任务合为一体，共同起到提高揭错特征质量的目的。

8.1 揭错特征的自然语言抽象能力
本节的例子证明了由大语言模型生成的揭错特征具备强大的语义抽象能力。该能力能够剥离原始代码的具体实现细节，提炼出故障的核心模式，从而指导生成新的测试用例，以探索更广泛的输入空间和边界情况，最终发现原始代码无法触发的深层缺陷。
对于HotSpot项目中编号为JDK-8239787的缺陷报告，LLM提取到了图片6中的原始Java代码片段和对应揭错特征:

图片 6 LLM提取到的HotSpot项目JDK-8239787缺陷报告的原始Java代码片段
Iterate over all Unicode characters up to 0xFFFF and invoke String.indexOf with an empty string and a negative offset, checking for incorrect match results. 
在这个例子中LLM使用该揭错特征作为新代码片段生成的参考得到了如图片7所示的新揭错片段，最后将该片段合成至原种子程序中得到可运行的新测试用例。

图片 7 LLM基于JDK-8239787揭错特征生成的Java代码片段
可以观察到新生成的揭错片段与原始片段的几处不同：（1）修改了循环的边界条件（2）将indexOf方法的调用对象和参数进行了反转。该片段的语义与原始片段相同，但是由于自然语言的抽象性，生成了结构不同、边界情况变化的新片段。
当使用Eclipse OpenJ9 JVM (JDK 8 & JDK 11) 运行此新生成的测试用例时，程序会抛出NullPointerException异常，而这段代码预期执行现象为死循环。该问题已被OpenJ9项目确认为一个真实缺陷（Issue #22109）。
此案例证明，LLM生成的揭错特征成功表征了缺陷的深层逻辑。通过这种“抽象—实例化”的工作流，我们可以摆脱原始代码的束缚，创造出结构不同、但语义等价的新测试用例，从而有效拓展测试的边界，揭示出更隐蔽的潜在缺陷。这充分体现了高质量揭错特征在提升缺陷发现能力和研究价值方面的关键作用。
8.2 揭错特征的跨编译器迁移能力
本节的例子证明了由LLM生成的揭错特征具备有效的跨编译器迁移能力。该能力能够将一种编程语言中提炼出的抽象缺陷模式，成功应用于另一种语法结构迥异但语义概念相通的编程语言，从而指导发现目标编译器中的潜在缺陷。
对于HotSpot项目中编号为JDK-8261585的缺陷报告，LLM提取到了图片8所示的原始代码片段和对应揭错特征:

图片 8 LLM提取到的HotSpot项目JDK-8261585缺陷报告的原始Java代码片段
Create a weak reference to an object and conditionally trigger an uncommon trap by performing an impossible type check, simulating the scenario where a deoptimization occurs and improperly extends the lifetime of the referent object.
在这个例子中，LLM利用该Java语言特有的“弱引用”（WeakReference）和“去优化”（deoptimization）场景所蕴含的核心语义——即“在特定条件下执行一个不可能发生的类型检查以触发异常控制流”——作为指导，生成了一个适用于C++语言的新揭错片段，如图片9所示。

图片 9 LLM基于JDK-8261585揭错特征生成的C++代码片段
可以观察到新生成的揭错片段与原始片段存在显著的语言差异：（1）使用C++的智能指针std::weak_ptr和std::shared_ptr模拟Java的弱引用机制；（2）使用dynamic_cast对不兼容类型的指针进行转换，以模拟Java中不可能的instanceof检查。尽管两种实现的语言特性完全不同，但其要探索的底层编译器行为——即处理无效或边界性类型检查时的稳定性——是高度一致的。
当使用GCC编译包含此新片段的测试用例时，编译器抛出了“internal compiler error: error reporting routines re-entered”的严重错误，表明编译器前端在处理此类复杂、无效的嵌套表达式时出现了内部状态混乱。该问题已被提交至GCC官方缺陷跟踪系统（Bug #121408），并被开发人员确认为一个真实存在的编译器崩溃（ICE）缺陷。
此案例证明，自然语言描述作为一种强大的中间表示，成功地屏蔽了Java与C++之间的具体语法细节差异，保留了缺陷的本质逻辑。通过这种“抽象—实例化”的工作流，我们可以将从一种成熟编译器生态中挖掘的历史缺陷知识，有效地迁移到另一种编程语言中。这种思路为提升国产基础软件的测试广度和深度提供了切实可行的技术路径。这充分验证了本研究提出的跨软件揭错特征的有效性与通用性。
